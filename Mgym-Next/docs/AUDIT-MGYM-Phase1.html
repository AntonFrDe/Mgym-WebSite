Synthèse

Le dépôt contient une refonte Next.js jamais déployée. Le site réellement en ligne sur mgym.fr est un site distinct, construit avec Hostinger Website Builder, qui dispose déjà d'un éditeur visuel. Ce constat déplace l'argumentaire du projet : la cliente peut déjà éditer son site. Ce que le CMS apporte, c'est de l'éditer sans pouvoir casser le design, plus un planning structuré et un SEO maîtrisé.

Trois points bloquent le démarrage de la Phase 2 : le devenir du site Hostinger, le sort du pipeline de livraison hors-ligne, et une mise à jour de sécurité préalable. Ils sont détaillés en fin de document.

3. Point de vigilance : le scrollytelling

3.1 La contrainte documentée

Dans SentierActivites.js, lignes 78 à 107, chaque étape porte deux états séparés :

estOuvert   <- le clic sur « En savoir plus »
estVisible  <- l'IntersectionObserver au défilement

Le commentaire du code est explicite : « jamais remis à false : le clic ne touche jamais ce state ». Le bug historique venait d'un accordéon où le clic réinitialisait la classe posée par l'observateur, faisant disparaître l'étape.

Un troisième mécanisme opère en parallèle : useTraceAuScroll (lignes 34-73) mesure path.getTotalLength() une seule fois au montage et pilote strokeDashoffset au défilement.

3.2 Les trois ruptures introduites par le passage en dynamique

Ce ne sont pas des hypothèses : elles découlent directement du code lu.

#RuptureMécanisme et mitigation
1key={act.name}
SentierActivites.js:195
CarrouselActivites.js:151		 Le titre sert de clé React. Dès qu'une faute est corrigée dans Sanity, React voit une clé différente, démonte l'étape et la remonte avec estVisible = false : l'étape disparaît jusqu'à ce que l'observateur la revoie — or l'utilisateur a déjà défilé.
Mitigation : clé = _id Sanity, stable à la renomination. Non négociable.
2const SENTIER = buildPath(activities.length)
portée module, ligne 32		 Le tracé SVG est calculé à l'import, sur un tableau statique. Avec des données dynamiques, le nombre d'activités devient variable.
Mitigation : déplacer le calcul dans le composant, mémoïsé sur la longueur du tableau.
3useTraceAuScroll
dépendances [pathRef, wrapRef]		 Des refs, donc stables : l'effet ne s'exécute qu'une fois. Si le d du chemin change après le montage, le strokeDasharray reste calculé sur l'ancienne longueur.
Mitigation : ajouter la longueur du chemin aux dépendances.

La décision qui neutralise les trois d'un coup
Récupérer les données de Sanity au moment du build, pas dans le navigateur. En génération statique, les composants reçoivent leur tableau d'activités complet au premier rendu : la rupture 1 reste à corriger, mais les ruptures 2 et 3 ne peuvent plus se produire, puisque rien ne change après le montage. C'est le mode de rendu qui protège l'animation, pas du code défensif.

Un rendu côté client casserait aussi le filet de sécurité : le site Next n'a pas le setTimeout de 3 secondes qui existe dans build-standalone.js (lignes 99-102). Une étape montée après que l'utilisateur l'a dépassée resterait invisible indéfiniment.

5. Stratégie de rendu : production contre prévisualisation

5.1 Le conflit, tranché par l'expérience

Le cahier des charges accepte une production statique et une prévisualisation dynamique, et rend la prévisualisation obligatoire. Or next.config.js contient output: 'export'.

Le conflit n'a pas été supposé mais testé : copie jetable du projet, ajout d'une route /api/preview utilisant draftMode(), puis build.

Error: export const dynamic = "force-static" not configured on route
       "/api/preview" with "output: export"
> Build error occurred

output: 'export' et la prévisualisation sécurisée sont mutuellement exclusifs dans une même configuration. C'est définitif.

5.2 Ce que cela n'implique pas

output: 'export' n'est pas synonyme de « site statique ». Next hébergé sur un runtime Node génère tout de même l'intégralité du HTML au build et le sert depuis un CDN. Le référencement et les performances sont identiques. Le drapeau export ne sert qu'à produire un dossier out/ portable.

5.3 Architecture recommandée

next.config.js  ->  retirer output: 'export' du build par défaut
Hébergement     ->  Vercel / Netlify / Cloudflare Pages (runtime Node)
Production      ->  génération statique, contenu publié uniquement, servi par CDN
Preview         ->  draftMode() + route validant un secret, no-store, noindex
Publication     ->  Sanity publish -> Deploy Hook de l'hébergeur

Le Deploy Hook présente un avantage de sécurité décisif : aucune API publique à écrire, donc aucune signature à vérifier, aucune limitation de débit à implémenter. La surface d'attaque disparaît par construction plutôt que par mitigation.

5.4 La contrepartie : le pipeline de livraison hors-ligne

build-standalone.js (344 lignes), serve.js (93 lignes) et le dossier Livraison-MGYM/ dépendent de out/. Ils existaient pour montrer le site à la cliente avant mise en ligne, par courriel ou Google Drive — c'est précisément ce que la prévisualisation Sanity remplace, en mieux.

OptionDécisionConséquence
1Retirer le pipeline (environ 450 lignes)Sa fonction est reprise par la preview. Perte : plus de copie hors-ligne
2Le conserver via un second mode de buildLa route de preview devrait être exclue de ce build — non supporté nativement par Next
3Le réécrire pour aspirer le site déployéRecommandée. Préserve la fonctionnalité, supprime le couplage à output: 'export', simplifie le script

9. Contradictions résiduelles

  1. La documentation du projet contredit la mission. CLAUDE.md interdit encore TypeScript et toute dépendance hors des trois socles. À amender en Phase 2, sinon la documentation contredira le code livré.
  2. Le cahier des charges fixe mgym.fr comme site public. Or ce domaine sert aujourd'hui un autre site, avec un blog déjà en place. Basculer signifie remplacer le site actuel de la cliente, pas en publier un nouveau. Ce n'est pas un détail technique mais une décision commerciale.
  3. Le blog existe déjà sur mgym.fr/blog-list, vide. La mission le traite comme une fonctionnalité neuve.

Annexe — méthode de vérification

Toutes les affirmations de ce document reposent sur une observation directe :

  • Lecture intégrale des 21 fichiers source, de globals.css, des scripts de build et de la documentation du dépôt.
  • Relevé des numéros de ligne par recherche automatisée, puis vérification manuelle de chaque plage citée.
  • npm audit sur l'arbre de dépendances installé.
  • Analyse de l'historique git complet, toutes branches, sur les sources versionnées, binaires et bundles générés exclus.
  • Résolution DNS et requêtes HTTP sur mgym.fr, www.mgym.fr, admin.mgym.fr, interrogation RDAP de l'AFNIC.
  • Test de compatibilité output: 'export' exécuté dans une copie jetable du projet, supprimée après usage.
